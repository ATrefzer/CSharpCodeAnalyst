# Generierter Code

## Schritt 1: Welche Dateien es gibt und wie sie hereinkommen

Es gibt genau **zwei Türen** in den Graph. Danach ist alles gleich.

| Datei                                                        | Wer schreibt sie         | Tür              | Elemente daraus                          |
| ------------------------------------------------------------ | ------------------------ | ---------------- | ---------------------------------------- |
| `obj\…\MainWindow.g.cs`                                      | WPF-Markup-Compiler      | A                | `Connect`, die `x:Name`-Felder           |
| `obj\…\GeneratedInternalTypeHelper.g.cs`                     | WPF-Markup-Compiler      | A                | die Hilfsklasse                          |
| `Resources\Strings.Designer.cs`                              | resx-Designer            | A                | `ResourceManager`, jeder String-Getter   |
| `obj\…\AssemblyInfo.cs`, `GlobalUsings.g.cs`                 | .NET SDK                 | A                | keine (nur Attribute/Usings)             |
| `[ObservableProperty]`, `[RelayCommand]`, `[GeneratedRegex]` | Roslyn, zur Compile-Zeit | B                | die generierten Properties/Commands      |
| `MainWindow.xaml` selbst                                     | du                       | *(dritter Pass)* | keine – das ist der XAML-Linker, kein C# |

**Tür A – Dateien auf der Platte.** Das sind ganz normale `Compile`-Items. `CollectAllFilePathInSolution` sammelt alles aus `project.Documents` in `_projectFilePaths`, und die Schleife über `compilation.SyntaxTrees` lässt durch, was `IsProjectFile` bejaht. Diese Dateien waren **schon immer** drin – sie hatten mit der alten Option nie etwas zu tun.

**Tür B – Source-Generatoren.** Die stehen nicht in `project.Documents` und ihre Syntaxbäume nicht in der Compilation. Sie müssen extra geholt werden: `project.GetSourceGeneratedDocumentsAsync()`. Genau das war die alte Option. Jetzt passiert es immer.

Beide Türen führen in dieselbe Methode, `ProcessNodeForHierarchy` – ab da gibt es keinen Unterschied mehr.

## Schritt 2: Beim Durchlaufen wird notiert, welche Datei generiert ist

Während Phase 1 läuft, füllt sich ein Set `_generatedFilePaths`:

- Tür A: `GeneratedCode.IsGeneratedFile(syntaxTree)` – Dateiname (`.g.cs`, `.g.i.cs`, `.designer.cs`, `.generated.cs`, `.AssemblyAttributes.cs`, `TemporaryGeneratedFile_*`) **oder** ein `<auto-generated>`-Kommentar vor dem ersten Token.
- Tür B: ohne Prüfung – ein Source-Generator-Dokument ist es per Definition.

Das ist erst mal nur eine Liste von Pfaden. Es wird noch nichts markiert.

## Schritt 3: Markieren, wenn alles gelaufen ist

Am Ende von Phase 1 läuft `MarkGeneratedElements()` einmal über alle Knoten:

> Ein Element ist generiert, wenn es mindestens eine `SourceLocation` hat und **alle** davon in generierten Dateien liegen.

Warum erst am Ende und warum „alle": eine Code-Behind-Klasse ist `partial`. `MainWindow` hat zwei Deklarationen – deine in `MainWindow.xaml.cs` und die des Markup-Compilers in `MainWindow.g.cs`. Ein Element, zwei Locations. Beim Durchlaufen weiß man noch nicht, ob noch eine dritte kommt.

Das Ergebnis im echten Lauf:

```
IsGenerated=False  MainWindow               (2 Deklarationen)  → deine Klasse
IsGenerated=True   MainWindow.Connect       (1 Deklaration)    → nur in .g.cs
IsGenerated=True   MainWindow.TreeControl   (1 Deklaration)    → das x:Name-Feld
```

Deine Hälfte bleibt deine. Nur was ausschließlich in der generierten Hälfte existiert, wird markiert.

## Schritt 4: Phase 2 braucht keine Regel

`RelationshipAnalyzer` läuft über die Elemente, die Phase 1 angelegt hat, und holt sich den Syntax über `DeclaringSyntaxReferences` des Symbols. Es gibt dort keinen Dateifilter. Was Phase 1 angelegt hat, wird analysiert – egal aus welcher Tür.

Deshalb hält `Connect` die Event-Handler am Leben, und deshalb hält eine generierte Property ihr Backing-Field am Leben.

## Wer die Markierung heute benutzt

Nur einer: die Dead-Code-Analyse setzt daraus die Notiz `Generated code` (83 von 866 Findings). Sonst niemand – Metriken, Zyklen, DSM und der XAML-Linker sehen die Markierung nicht an. Sie ist eine reine Beschriftung, keine Verhaltensänderung.

## Grenzen, die du kennen solltest

- **Projekt-Ausschluss geht vor.** `ShouldAnalyzeProject` filtert vorher nach `.csproj` und dem Regex-Filter. Ein ausgeschlossenes Projekt bringt auch keinen generierten Code mit.
- **`.g.i.cs` ist in der Namensliste, taucht in dieser Solution aber nicht auf.** Bei MSBuildWorkspace kommt hier `.g.cs` in die Compilation. Die Regel deckt es ab, falls es woanders anders ist.
- Nicht erkannt wird eine `.cs`-Datei, die ein Nicht-Roslyn-Werkzeug auf die Platte schreibt, wenn sie weder einem bekannten Namensmuster folgt noch einen `<auto-generated>`-Header trägt. Roslyns eigene Analyzer haben dieselbe Lücke (z.B. T4)
- Ein einzelner generierter Member in einer sonst handgeschriebenen Klasse wird markiert; die Klasse nicht. Das ist so gewollt.

# Dead Code Analysis

Der Algorithmus in einem Satz: **Ein Element ist tot, wenn keine Beziehung aus dem Produktivcode in seinen Teilbaum hineinführt.**

Alles andere sind Verfeinerungen davon. Hier der Ablauf.

------

## Schritt 1: Kanten sortieren (`CollectEdges`)

Jede Beziehung im Graph landet in genau einem von drei Töpfen.

| Beziehung                                                    | Topf            | Warum           |
| ------------------------------------------------------------ | --------------- | --------------- |
| `Calls`, `Uses`, `Creates`, `Invokes`, `UsesAttribute`, `Inherits` | **Verweise**    | echte Benutzung |
| `Implements`/`Overrides`, **ausgehend von einem Member**     | **Polymorphie** | siehe Schritt 3 |
| `Containment`, `Bundled`, `Handles`                          | **verworfen**   | keine Benutzung |

`Containment` ist die Eltern-Kind-Hierarchie. `Bundled` malt nur die Graphansicht. `Handles` zeigt vom Handler zum Event – die Registrierung `x.Click += OnClick` erzeugt daneben eine `Uses`-Kante, die den Handler am Leben hält.

Ausnahme bei der Polymorphie: `class C : IFoo` geht **vom Typ** aus. Das ist ein normaler Verweis, denn `IFoo` steht in Cs Deklaration. Nur wenn ein *Member* implementiert, ist es Polymorphie.

## Schritt 2: Die Kernregel (`MarkReferenced`)

Für jede Verweiskante wird markiert, was sie „von außen betritt".

Beispiel: `B.M` ruft `A.M`.

```
1. Kette der Quelle nach oben sammeln:   B.M → B → Namespace → Assembly
2. Vom Ziel nach oben laufen und markieren, bis man diese Kette trifft:
      A.M    markieren
      A      markieren
      Namespace  ← steckt in der Quellkette → Stopp
```

Ergebnis: `A.M` und `A` sind referenziert. Der gemeinsame Namespace nicht.

Zwei Dinge folgen daraus, und beide entsprechen dem, was man von Hand urteilen würde:

- **Eine Klasse lebt, wenn eines ihrer Member benutzt wird** – auch wenn die Klasse selbst nie genannt wird.
- **Eine Klasse kann sich nicht selbst am Leben halten.** Rufen ihre Methoden nur einander auf, bleibt jede dieser Kanten *innerhalb* des Teilbaums. Der Lauf stoppt sofort. Die ganze Klasse ist tot.

## Schritt 3: Polymorphie umdrehen (`PropagateContractUsage`)

`Implements`/`Overrides` zeigt von der Implementierung **zum** Contract. Als Verweis gezählt wäre beides falsch:

- Jedes Interface-Member sähe benutzt aus (die Implementierung „verweist" ja darauf).
- Jede Implementierung sähe unbenutzt aus (auf sie zeigt nichts).

Also wird die Lebendigkeit stattdessen in die andere Richtung geschoben: **Wird `IService.Run` aufgerufen, leben alle Implementierungen von `Run`** – und die Typen, die sie enthalten. Transitiv, denn ein Override kann selbst überschrieben werden.

Wird der Contract nie aufgerufen, stirbt er zusammen mit seinen Implementierungen. Genau das will man sehen.

Zeigt der Contract nach draußen (`ICommand.Execute`, `object.GetHashCode`), können wir den Aufrufer nicht sehen. Das macht **nicht** lebendig, sondern erzeugt nur eine Notiz.

## Schritt 4: Zweimal laufen, in zwei Farben (`ComputeReferenced`)

Schritt 2 und 3 laufen zweimal über dieselben Kanten:

- **`All`** – alle Kanten.
- **`FromProduction`** – nur Kanten, deren *Quelle* nicht in einer Test-Assembly liegt.

Eine Test-Assembly ist eine, die mindestens ein Element mit Testattribut enthält (`[Test]`, `[Fact]`, `[TestFixture]`, …).

Wichtig: Die Contract-Propagation läuft **pro Farbe**, nicht einmal am Ende. Ruft die UI `ICodeGraphExplorer.FindIncomingCalls`, lebt die Implementierung produktiv. Ruft nur ein Test sie, nicht. Eine gemeinsame Propagation würde jede Implementierung eines Contracts, den irgendein Test benutzt, für produktiv erklären.

Daraus ergibt sich:

| in `All` | in `FromProduction` | Bedeutung                  |
| -------- | ------------------- | -------------------------- |
| ja       | ja                  | lebendig                   |
| ja       | nein                | **nur von Tests benutzt**  |
| nein     | nein                | **gar nicht referenziert** |

## Schritt 5: Melden (`Report`)

Jetzt geht es einmal über alle Knoten. Vier Filter, in dieser Reihenfolge:

**1. Ist es überhaupt ein Fund?** (`IsReported`)

- Assemblies, Namespaces und externe Elemente sind nie Kandidaten.
- Steht es in `FromProduction`? → lebendig, fertig.
- Sonst: gar nicht referenziert **oder** nur von Tests. Letzteres zählt nur *außerhalb* einer Test-Assembly – innerhalb ist „von Tests benutzt" ja der Zweck eines Helfers.

**2. Serialisierte Property?** Eine public Property auf einem Typ mit `[Serializable]`, `[DataContract]`, `[JsonObject]` … wird fallengelassen. Der Serializer greift per Reflection zu; auf so einem Typ wäre jede Property ein Fund.

**3. Roll-up.** Würde der Parent auch gemeldet, überspringen. Eine tote Klasse ergibt eine Zeile, nicht eine pro Methode.

**4. Notizen und Confidence sammeln** (`CreateFinding`).

## Die Notizen

Zwei Sorten. **Zweifel** – der Verweis könnte da sein, wo der Parser nicht hinsieht:

| Notiz                             | Woher                                              |
| --------------------------------- | -------------------------------------------------- |
| `Entry point`                     | `Main`, statischer Konstruktor, `GlobalStatements` |
| `Test code`                       | Testattribut im Teilbaum                           |
| `Attributes: …`                   | irgendein Attribut im Teilbaum                     |
| `Implements external contract: …` | aus dem `ExternalContractStore` des Parsers        |
| `Generated code`                  | `CodeElement.IsGenerated`                          |

**Erklärungen** – der Fund ist verstanden, die Notiz nennt, was mitstirbt:

| Notiz                             | Woher                                                        |
| --------------------------------- | ------------------------------------------------------------ |
| `Implemented but never called: …` | Sieht den **Contract**: mich implementieren A und B, aber niemand ruft durch mich hindurch. |
| `Implements unused contract: …`   | Sieht die **Implementierung**: der Contract, den ich erfülle, ist selbst tot |
| `Used only by tests: …`           | plus die Namen der Tests                                     |

Entry-Point-, Test- und Attribut-Notizen werden über den **ganzen Teilbaum** gesammelt. Gemeldet wird eine tote Klasse – aber die `[Test]`-Attribute hängen an ihren Methoden.

Gleicher Code in allen drei Fällen, nur der Aufrufer wechselt:

```csharp
public interface IService { void Run(); }

public class ServiceA : IService { public void Run() { } }
public class ServiceB : IService { public void Run() { } }

public class Factory                       // hält beide Klassen am Leben,
{                                          // ruft Run aber nie
    public object MakeA() => new ServiceA();
    public object MakeB() => new ServiceB();
}
```

**Fall 1 – niemand ruft `Run`**

```
IService.Run   ContractNeverCalled      → ServiceA.Run, ServiceB.Run
ServiceA.Run   ImplementsDeadContract   → IService.Run
ServiceB.Run   ImplementsDeadContract   → IService.Run
```

Drei Zeilen. Der Contract nennt seine beiden Implementierungen, jede Implementierung nennt den Contract.

**Fall 2 – zusätzlich `b.Run()` direkt auf `ServiceB`**

```csharp
public class Caller { public void Go(ServiceB b) { b.Run(); } }
```

```
IService.Run   ContractNeverCalled      → ServiceA.Run, ServiceB.Run
ServiceA.Run   ImplementsDeadContract   → IService.Run
```

`ServiceB.Run` verschwindet – es hat eine eingehende Kante. Der Contract bleibt gemeldet, denn *durch das Interface* ruft weiterhin niemand. Und er listet weiter **beide** Implementierungen: die Liste sagt „wer mich implementiert", nicht „wer mit mir stirbt".

**Fall 3 – `s.Run()` über das Interface**

```csharp
public class Caller { public void Go(IService s) { s.Run(); } }
```

```
(nichts)
```

`IService.Run` ist referenziert, die Propagation macht beide Implementierungen lebendig.



## Die Confidence

Drei Regeln, in dieser Reihenfolge:

1. **Low** – eine der Zweifel-Notizen (Entry Point, Test Code, Attribute, externer Contract) ist gesetzt. Wir wissen schon, dass wir falsch liegen könnten.
2. **High** – keine solche Notiz, und das Element **oder einer seiner Container** ist `private`/`internal`. Dann fallen „nichts referenziert es" und „nichts *kann* es referenzieren" zusammen.
3. **Medium** – alles andere: public, protected, oder Sichtbarkeit unbekannt.

Zwei Abzüge von High:

- Eine public Property auf einem Typ, der `INotifyPropertyChanged` implementiert. Ein `{Binding}` erreicht genau das, und Bindings verfolgt der Parser bewusst nicht.
- Ein `Used only by tests`-Fund. Etwas referenziert es ja nachweislich – ob ein Test allein das Behalten rechtfertigt, ist eine Entscheidung, keine Messung.

## Was der Algorithmus bewusst *nicht* tut

**Keine Kaskade.** Gemeldet wird, was *jetzt* unreferenziert ist. Sitzt der einzige Aufrufer von `Formatter` in der Klasse `Report`, die du gerade gemeldet bekommen hast, ist `Formatter` **kein** Fund – er ist referenziert, von totem Code. Lösche den Fund und lass es nochmal laufen, dann kommt die nächste Schicht.

Eine frühere Version kaskadierte. Sie funktionierte, aber sie multiplizierte jeden Fehlalarm: ein unsichtbares `{Binding}` riss sieben weitere Elemente mit.

**Keine toten Zyklen.** Zwei Elemente, die nur einander referenzieren, halten sich gegenseitig am Leben. Das zu finden bräuchte Erreichbarkeit von einer expliziten Menge von Einstiegspunkten – eine andere Analyse als diese.
